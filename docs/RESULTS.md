# Results

Generated by `results/summarize.py` from the raw files in `results/`.

## Test environment and how to read these numbers

- One cloud VM: 2 vCPUs, Linux 6.18.44-fc-v310, ext4 on a virtual disk.
- **All nodes and all benchmark clients shared those vCPUs** and talked over loopback.
  There is no real network delay here. Across machines, latency will be higher.
- Measured fsync: 165 µs median, 300 µs p99. That is fast for a
  real SSD and may mean the hypervisor acknowledges flushes early. On disks with slower
  fsync, expect higher latency.
- Values were 128 bytes. Every write was fsynced before it was acknowledged.

## Can the tests actually catch bugs?

Each row rebuilds the system with one deliberate bug. 'Simulator' counts failing seeds out
of 5,000. 'Real chaos' runs up to three 30-second runs and stops at the first detection.

| Injected bug | Simulator | Caught as | Real chaos | Caught as |
|---|---|---|---|---|
| `no_dedup` | 4,865 / 5,000 | DOUBLE_APPLY, REALTIME_VIOLATION | caught on run 1 | DOUBLE_APPLY |
| `ack_before_commit` | 1,793 / 5,000 | LOST_WRITE, REALTIME_VIOLATION | caught on run 1 | LOST_WRITE |
| `vote_ignores_log` | 3,095 / 5,000 | LEADER_COMPLETENESS | not caught (3 runs) | — |
| `commit_old_term` | 0 / 5,000 | — | not caught (3 runs) | — |
| `stale_read` | 930 / 5,000 | REALTIME_VIOLATION | not caught (3 runs) | — |
| `forget_vote` | 39 / 5,000 | ELECTION_SAFETY | not caught (3 runs) | — |
| `skip_fsync` | 2,823 / 5,000 | LEADER_COMPLETENESS, LIVENESS, LOG_MATCHING | not caught (3 runs) | — |
| `no_truncate` | 1,783 / 5,000 | DIVERGENT_READ, LEADER_COMPLETENESS, LIVENESS, LOG_MATCHING, LOST_WRITE, SAFETY_ABORT, STATE_MACHINE_SAFETY | caught on run 2 | CONVERGENCE |
| `snapshot_drops_sessions` | 2,215 / 5,000 | DIGEST_MISMATCH, DIVERGENT_READ, LOST_WRITE, REALTIME_VIOLATION | caught on run 1 | CONVERGENCE, DIVERGENT_READ |

`commit_old_term` (Figure 8 of the Raft paper) needs a very specific interleaving. It is
caught by the directed test `figure8_mutation_is_detected`, not by random search.

Real-process chaos caught 4 of the 9 bugs in these short runs, and missed some that can lose
writes (`vote_ignores_log`, `skip_fsync`). Those need rare timing or a real power cut, so a clean chaos
pass is not proof on its own. The simulator and directed tests cover what chaos misses.

`skip_fsync` shows why both layers exist: SIGKILL does not lose data held in the kernel page
cache, so real-process chaos cannot see a missing fsync. The simulated disk can.

## Limits of this evidence

- No client reached its 6-second deadline in the chaos runs, so `Indeterminate` outcomes were exercised only in the simulator.
- SIGKILL produced no torn log tails, because each write reached the kernel whole. Torn-write recovery is covered by
  `torn_write_at_every_byte_recovers_a_clean_prefix` and the simulator, not by the chaos runs.
- Real power loss was not tested. Everything ran on one host, so real network behaviour was only approximated by the proxy.
- An earlier chaos batch was thrown away after a harness bug stopped one node from ever starting (see `chaos_before_port_fix.jsonl`).
  The 24 runs above came after that fix.
- After this campaign one more harness fix landed: a race in the test proxy crashed the harness once during a mutation run,
  and that run was repeated. Only test code changed; the server code is the code measured here.
